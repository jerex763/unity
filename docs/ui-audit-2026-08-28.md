# Unity UI audit — 2026-08-28

## Scope and method

This audit follows the project-scoped `redesign-existing-projects` skill's
scan/diagnose/focused-fix workflow. Evidence includes the three-worker phone
session, a read-only review of the deployed demo at 390 × 844 and 1440 × 1000,
the React page structure, and the current monolithic CSS file.

No application code or live data was changed. The audit deliberately rejects
the skill's marketing-oriented motion, decorative imagery, broken grids and
framework/library changes. Unity is a trust-first operational application, not
a landing page.

## Design read

Unity is a mobile-first internal church operations tool used under time pressure
by Pastors, check-in workers and follow-up workers. It should feel calm, humane,
clear and dependable. The existing leaf green and warm cream are appropriate;
the main problem is weak task hierarchy and excessive repeated presentation,
not the palette.

The design target is **quiet operational clarity**:

1. Always show the user's church, role and current work context.
2. Put the next action before introductory copy and decoration.
3. Give each mobile screen one primary job.
4. Make state changes visible and reversible where appropriate.
5. Keep personal/contact data readable without turning every row into a form.
6. Use cards only when they group a real task or record.
7. Preserve native React/CSS, accessibility and reduced-motion behavior.

## Overall diagnosis

The interface is consistent but overly templated. Most routes repeat the same
large heading, uppercase eyebrow, explanatory paragraph, white rounded card and
green/outlined button pattern. This creates visual consistency without useful
priority. Operational controls often start below the first viewport, while
secondary descriptions and contact controls consume the most space.

On desktop the same pattern produces very low information density and large
unused areas. On mobile it produces long pages, hidden detail and button stacks.
The resulting friction matches the worker feedback: people can finish the job,
but they must discover where the real work is and repeatedly scroll to it.

## Recommended information architecture

### Mobile shell

- Keep the bottom navigation.
- Replace the hidden top-right context with a compact second line such as
  `Fictional Test Church · Pastor`.
- Keep Sign out inside a small account menu so church context has priority.
- Reduce page introductions after the first visit; operational pages should use
  a compact title row rather than a marketing-style hero.

### Home

- Make `Your next actions` the first and dominant section.
- Render Call, WhatsApp and Open follow-up as proper 44px touch targets.
- Make overdue/due-today state prominent and use tabular date figures.
- Remove or greatly compact shortcut cards that duplicate bottom navigation.

### People directory and profile

- Use one search field plus a `Filters` button that opens a compact filter sheet.
- Make the entire person summary row open the profile and include an explicit
  `View` affordance for clarity.
- Show at most the preferred contact action in the directory; keep full contact
  details in the profile.
- In the profile, place `Edit person` in the title row and keep it visible.
- Present contact values as text rows with separate Copy/Call/Message buttons,
  not as disabled-looking inputs.
- On save, close editing, focus the profile heading, reveal the updated summary,
  and show a short non-blocking Saved status.

### Events and registrations

- Give the event card two primary actions: `Check in` and `Registrations`.
- Put Edit, Duplicate and public-link management in a clearly labelled overflow
  or secondary action area.
- Open registrations as a dedicated mobile route or full-screen sheet. Do not
  expand a second application inside the bottom of the event card.
- Create a persistent `Public registration` section with Active/Off status,
  explanatory copy and a safely worded replacement action. If the raw link is
  not recoverable, say so before offering replacement.

### Check-in

- Preserve the current task-first structure and `To check in / All / Checked in /
  Walk-ins` filters.
- Keep search and filters sticky while the attendee list scrolls.
- Change the hint to describe scope: registration list by partial name.
- In Add walk-in, show suggestions after two characters and offer a bounded
  `Search eligible people` path. Do not expose an unconditional all-people
  dropdown.

### Follow-ups

- On mobile, tapping a queue item should navigate to or open a full-screen task
  detail. The queue should not remain above the selected task.
- Put person, next action, due date and preferred contact action in the first
  viewport.
- Focus the dialog heading/close control rather than the Stage select.
- Rename Engagement to `Likelihood of continued engagement` with brief option
  help, or remove it from the pilot update form until it drives a decision.
- Explain that Stage records workflow progress, Interaction records contact,
  and Outcome records the result.
- Display saved Outcome and latest interaction in the task summary.
- Format display dates consistently as `DD/MM/YYYY`; keep the native date input
  for mobile reliability.

## Visual system adjustments

Do not start with a font or palette replacement. Start with hierarchy.

- Reduce operational page H1 size to approximately 1.75–2.25rem on mobile and
  2.25–3rem on desktop.
- Remove most uppercase eyebrows; retain them only where they convey a genuine
  workflow category.
- Define a small spacing scale and reduce large gaps before forms/lists.
- Keep green as the single action accent and cream as the page background.
- Use status colors only for real workflow states; do not use urgent color for
  ordinary decoration.
- Establish three button levels: primary task, secondary task, and quiet utility.
- Standardize minimum touch height at 44px.
- Use one compact row pattern for directory, roster and queue records rather
  than a different large card composition for each.
- Use skeletons only where loading is perceptible; otherwise reserve layout and
  show concise progress.

## Implementation batches

### Batch 1 — context and task completion (recommended first)

1. Show active church and role on every mobile route.
2. Convert Home actions into proper touch targets and strengthen due state.
3. Make person rows fully navigable; move Edit to the profile header.
4. Restore focus/scroll and visible confirmation after profile/follow-up saves.
5. Stop auto-focusing the Follow-up Stage selector.
6. Display Outcome and consistently formatted dates.

This batch directly addresses repeated worker findings and should not introduce
new dependencies or schema changes.

Implementation status: the user approved this batch and it is implemented in
the local working tree under Issue #110. Prettier, ESLint, 109 Vitest tests, the
production build and 35 Playwright checks across 320, 375, 390, 430 and desktop
widths pass. The browser checks include visual bounds for long church context
and edit-entry/post-save feedback beneath the sticky header. Independent review

### Batch 2 — mobile workflow structure

1. Move registrations to a full-screen mobile flow.
2. Move selected follow-up detail to a full-screen mobile flow.
3. Compact directory contact actions and move filters into a sheet.
4. Clarify check-in and walk-in search scope/suggestions.
5. Redesign public-link status and replacement wording.

### Batch 3 — visual-system consolidation

1. Introduce shared row, action-bar, status, date and feedback primitives.
2. Break page-specific styles out of the global stylesheet without changing the
   framework or styling approach.
3. Reduce repeated card/eyebrow/hero patterns and tune desktop density.
4. Add proportional visual regression coverage at 320, 375, 390, 430 and
   desktop widths.

## Explicit non-goals

- No Tailwind, component-library or routing-framework migration.
- No parallax, cinematic motion, glassmorphism, noise textures or decorative
  stock imagery.
- No new registration fields from visual feedback alone.
- No all-church name dropdown on the event-day screen.
- No role, tenancy, privacy, public-token or data-model changes hidden inside a
  UI redesign.

## Acceptance standard

The redesign is successful when each role can identify church context, locate
the primary action, complete it, and verify the saved result within the same
mobile viewport flow. Visual polish is secondary to that observable outcome.
