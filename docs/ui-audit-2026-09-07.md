# Unity 前端 UI/UX 复审 — 2026-09-07

## 结论与边界

建议先修复失败恢复、请求进行中的反馈、列表到详情的连续性，再做有范围的视觉调整。现有 People/Profile 草图是待验证选项，不能因已经画好就优先实施。

本轮采用 `frontend-design` 的内容/任务/层级/克制原则，并参考 [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md) 检查表单、导航状态、焦点和恢复能力。营销页面的字体替换、动效和视觉“独特性”要求不直接套用到教会操作工具。44px 是本项目的交互目标；本报告不是完整 WCAG 合规认证。

基线：应用代码来自 `fd7a6fd`，上一轮未提交的交接文档和 mock 保留。源码检查覆盖 Shell、Home、Directory、Profile、Events、Check-in、Follow-ups、公开报名/取消、登录及共享联系/模态组件。通过本地 Vite + Playwright Chromium 拦截 API 展示真实 React 页面；主视口 390×844，Directory 另检查 1280×900。使用 12 个虚构人员、12 条虚构跟进和 1 个活动。没有访问真实人员数据，没有向后端提交写入。

本轮没有重跑全套回归，也没有把开发服务器性能当生产性能。未检验真机软键盘、Safari、VoiceOver、中文长文本、真实列表规模和真实操作频率。旧有五个屏宽的 Chromium 回归不能代替这些证据。

## 一、事实、假设、偏好

### 已确认事实

1. Batch 1 的手机教会/角色提示、整段人员摘要入口、Profile 顶部 Edit、保存反馈和 Follow-up 模态标题焦点已存在，应保留。
2. 390px 模拟中，含 WhatsApp/WeChat/电话/邮箱的单条 Directory 卡片高约 **486px**。12 条同结构记录使页面约 6432px 高。这个数字只适用于当前样本，不能概括为所有真实记录。
3. Profile 的邮箱只读 textarea 可见高度 **33px**、内容高度 **88px**，电话 **33px / 51px**。按钮占据横向空间，文本虽然可复制，但默认没有完整呈现。现有样式仍保留 `rows={1}` 的 textarea。
4. 12 条 Follow-up 模拟中，点击第一条后详情顶部位于视口坐标约 **2587px**，`scrollY=0`；Events 展开 roster 后顶部约 **752px**，位于 844px 视口底部附近。点击能改变状态，但结果不够可见。
5. Profile 详情 GET 返回模拟 503 后，仍显示 Loading，没有出现 error 页面，并产生未处理 Promise 错误。错误处理接在另一个目录请求后面。
6. Directory 搜索后进入 Profile，再按浏览器返回，搜索值清空。Home 中“打开某人的跟进”链接也只进入 `/follow-ups`，没有携带该任务 ID。
7. 将签到响应延迟 1.2 秒，双击 Check in 发出 **2 个 POST**，等待期间按钮仍可用。这证明前端缺少 pending 防护；没有据此断言后端产生两条签到记录。
8. 公开报名 GET 的模拟 503 显示“链接可能过期或被撤回”，没有重试入口。代码把所有加载失败统一归入该状态，不能区分暂时故障和失效链接。
9. 主样本没有页面级横向溢出。但 Directory 的筛选条横向滚动并隐藏滚动条，第三个筛选器只露出部分；“页面不溢出”不能代表所有控件都可发现。

### 仍待验证的假设

- 志愿者主要在手机上、短时且有干扰地操作：项目定位与三人反馈支持，但缺少设备/时长记录。
- Directory 的主要任务是识别人，而非直接联系：尚无频率证据。
- 修改资料通常只改一个区块：尚无跨字段编辑记录。
- 活动日签到远比编辑活动频繁：合理但未量化；活动筹备阶段可能相反。
- 当前工作人员对 Stage / Engagement / Outcome 的困惑已被新说明解决：只确认实现，未确认新一轮人测。

### 设计偏好，而非客观结论

- 保留叶绿 `#2f6b4f`、奶油底 `#fbf8f1` 和现有字体栈，倾向低装饰、紧凑工作界面。
- 减少大标题、重复 eyebrow、重复边框，让人员/任务/状态成为视觉中心。
- 桌面偏向紧凑列表与适量分栏，手机偏向单任务详情。

这些偏好应服从可读性和任务完成证据。换字体、去圆角或换组件库并不能自动改善效率；不能因某种风格“像 AI”而判其不合格。

## 三、可行选择比较

### 总体改造路线

| 方案 | 得到什么 | 代价/缺点 | 何时适合 |
|---|---|---|---|
| A：局部可靠性修复 | 快速解决无限 Loading、裁切、重复请求和错误提示 | 队列到详情仍可能显得拼接 | 临近试用、时间紧、记录很少 |
| B：先可靠性，再按任务重组（推荐） | 保留现有技术和视觉体系；把 mobile selection → detail → save → back 做完整 | 需要定义路由/返回/未保存状态，并补真实交互验证 | 手机工作流是核心，队列开始增长 |
| C：全面设计系统/布局重写 | 有机会统一组件和风格 | 验收面大，原有权限/焦点行为容易回退，可能只是换皮 | 多团队扩展、品牌变化或现有结构已被证明妨碍持续交付 |

当前证据支持 B，但第一阶段应能独立交付 A 的可靠性部分。没有证据支持换框架、引入组件库或先换全站字体。

### Directory：是否删除联系动作

| 选择 | 优点 | 风险 | 判断条件 |
|---|---|---|---|
| 只选人，进入 Profile 再联系 | 最容易扫读、低披露、结构简单 | 高频联系增加一次导航 | 若大多数操作确实是找人/看背景，选它 |
| 精简记录 + 一个联系入口 | 保留快速联系，避免全渠道控制堆叠 | 没有偏好渠道时要有明确 fallback；操作不可嵌套在整行 Link 内 | 当前可优先拿去对比的折中方案 |
| 保留全渠道但按需展开 | 同页处理多个渠道 | 仍有展开状态和长列表复杂度 | 仅当多人对比、多渠道切换是常见工作时 |

我不再把“删除全部目录联系动作”当成已证实的最佳方案。建议用第一、第二个版本做小规模任务对比。不要把单一联系按钮硬等同于 WhatsApp：未知偏好时应显示清楚的“联系”入口。

### Profile：就地编辑还是独立编辑页

| 选择 | 优点 | 代价/前提 |
|---|---|---|
| 紧凑资料页 + 单独完整编辑页 | 状态和保存边界最简单，跨字段编辑自然 | 小修改需要多一步，但可从区块锚点进入 |
| 分区就地编辑 | 读哪里改哪里，小改动上下文明确 | 必须证明区块独立；需要部分保存、取消、未保存跳转、错误焦点等完整设计 |
| 手机全屏编辑 sheet，桌面 dialog | 可以复用现有模态经验 | 长表单、键盘和退出恢复更容易复杂 |

对 Contact 和 Details 的展示去重可以独立推进；分区编辑不是必要前提。若试用常同时改姓名/身份/联系信息，优先完整编辑页。若多数修改仅一个独立区块，且部分保存安全，则分区编辑更有依据。

## 四、对上一轮草图的自我修正

1. “目录只负责选人”是产品假设，不是用户研究结论。
2. `people-profile-review-2026-09-07.html` 的桌面预览沿用了底部导航，而当前桌面是侧栏。没有证据支持这次导航改动，推荐保留现有桌面侧栏。
3. 草图的 Contact/Details 字段只是示意，不能作为完整字段与权限规格；身份字段的编辑入口、未保存导航和输入失败需要补齐。
4. 静态状态切换 + 40 组尺寸检查，只说明草图布局可展示，不说明真机键盘、焦点、API partial-save 和返回行为正确。
5. 保存后始终回顶部与始终回区块都过于绝对。应回到用户发起动作的上下文，并让更新结果可见。

## 五、视觉建议及成立条件

- 将主要列表页的大标题压至约 28–32px 手机、32–40px 桌面作为候选；以首个任务/搜索位置与文字缩放测试验证，不把数值当统一硬规则。
- Directory 候选记录以 88–112px 左右起步，姓名/身份/一行背景为主；允许长姓名增长，不能为了密度截掉关键身份线索。
- 同一任务区只突出当前主要操作。活动筹备时 Edit 可能合理；活动日应突出 Check-in 与 Registrations。先用明确、稳定的层级，暂不增加未经验证的自动模式切换。
- Check-in 现有四筛选及现有人/新访客分流应保留。候选调整是让搜索更早出现、Add walk-in 次一级；若大多数是现场首次来访，则应反转该层级。
- 保留现有桌面侧栏。先提升内容密度，再判断是否需要更多表格/分栏。宽屏不是放大手机版，也不必强制所有列表变表格。
- 保留当前调色板和字体栈，建立少量文字/间距/按钮层级 token。品牌辨识更适合来自清楚的教会/人员/任务上下文，而不是装饰动效。
- 公开报名保持单列。优先改善失败/重试、同意说明和成功后的私有取消链接留存指导；不要为了“更短”先隐藏已有联系渠道或新增联系字段。
- 登录页的 Church ID 是管理系统内部概念，若未来有实际多教会账户，可研究登录后明确选择教会。当前小范围账号发放场景不足以支持立即改认证流程。

## 六、下一步验证，及改变结论的条件

先修确定缺陷，再让同样三类工作人员做形成性验证。建议每人 10–15 分钟，自用手机、虚构数据；不收集人员姓名/牧养内容。设备/浏览器只记型号或类别。三个角色不是统计显著性样本，不据此宣称普遍效率提升。

任务建议：

1. Pastor：在 20–30 个虚构人员中定位指定人、修改一项资料、返回继续找下一人；分别尝试精简目录有/无联系入口。
2. 跟进同工：从 12–20 条任务中打开指定任务，联系、更新、回到原队列；从 Home 的指定人入口重复一次。
3. 签到同工：在 30–50 个虚构报名中找人签到，加一次现有人 walk-in；模拟 1–2 秒延迟和一次请求失败。
4. 另做工程验证：Profile 503/404、公开报名 503、保存失败保留值、离开未保存表单、iOS 键盘遮挡、200% 文字缩放、Tab/Shift+Tab/Escape、真实视口结果可见性。

记录是否独立完成、首次操作是否找对、误点/回退、是否知道保存成功、是否丢失搜索或输入，以及大致耗时。两个方案改变测试顺序，避免总让第二版占学习优势。仅增加时间指标不足以判断信任和理解。

改变结论的条件：

- 若目录直接联系是绝大多数动作，保留一个联系入口；若几乎不使用，则去掉。
- 若经常跨区块编辑，完整编辑页优先；若修改高度局部且部分保存可靠，再采用就地编辑。
- 若工作实际主要发生在桌面、频繁比较多人/任务，扩大主从布局或表格比手机式独立页更有价值。
- 若列表只有三五条且试用迫近，先交付局部修复，延后路由重组。
- 若真实弱网频繁，pending、重试和数据恢复优先级进一步提高；PWA 安装能力不能被当作离线业务保证。
