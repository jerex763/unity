# $0 fictional-data demo deployment

This runbook deploys the `codex/mvp-next` branch as one same-origin web service:

```text
GitHub codex/mvp-next
  -> Render Free Docker web service (React + Django + Admin)
  -> Neon Free PostgreSQL
```

This is a temporary evaluation environment, not production. Use fictional data
only. Do not enter real names, contact details, birthdays, religious information,
pastoral notes, care details, or other personal information.

## Why one web service

The React app uses Django session authentication and CSRF protection. Serving the
SPA, `/api/`, `/admin/`, and static assets from one Render origin avoids CORS and
cross-site cookie configuration. Public self-registration is not included; #93
tracks that future work.

## 1. Create the Neon Free database

1. Create a Neon Free project in a region close to Render Singapore.
2. In **Connect**, enable **Connection pooling**.
3. Copy the pooled connection string. Its host contains `-pooler` and the URL
   should include `sslmode=require` (Neon can also include
   `channel_binding=require`). This is the runtime `DATABASE_URL`.
4. Disable **Connection pooling** and copy the direct connection string. Its
   host does not contain `-pooler`. This is `MIGRATION_DATABASE_URL`.
5. Keep both URLs private. Never add them to Git, an Issue, or a screenshot.

The app uses the pooled URL for normal web requests. Schema migrations and
administrative commands use the direct URL because transaction-pooled
connections are not suitable for schema-changing operations. Production
settings enforce PostgreSQL and `sslmode=require` for both.

## 2. Create the Render Free service

1. In Render, choose **New > Blueprint** and connect `jerex763/unity`.
2. Select the `codex/mvp-next` branch and the repository `render.yaml`.
3. Confirm the service plan is **Free**, runtime is Docker, branch is
   `codex/mvp-next`, and health check is `/api/health/`.
4. When prompted, paste the Neon pooled URL into `DATABASE_URL`.
5. Paste the Neon direct URL into `MIGRATION_DATABASE_URL`.
6. Leave `DJANGO_SECRET_KEY` generated by Render.
7. Create the Blueprint and watch the first build and deploy logs.

The application derives `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` from Render's
automatic `RENDER_EXTERNAL_HOSTNAME` and `RENDER_EXTERNAL_URL` values. For a
future custom domain, set `DJANGO_ALLOWED_HOSTS` and
`DJANGO_CSRF_TRUSTED_ORIGINS` explicitly as comma-separated values.

The container requires both database URLs. Before every Gunicorn start it runs
`python manage.py migrate --noinput` with `MIGRATION_DATABASE_URL`, then starts
the web app with the pooled `DATABASE_URL`. Django migrations are repeatable,
and this avoids Render's paid pre-deploy command. Static files are collected
while the image is built, not on every startup.

## 3. Create fictional test access

Render Free does not provide an interactive shell. Create the initial
superuser with a one-off local command connected to the same Neon database:

```bash
cd backend
DATABASE_URL='paste-the-private-neon-direct-url-here' \
DJANGO_SETTINGS_MODULE=config.settings.prod \
DJANGO_SECRET_KEY='temporary-local-only-value' \
DJANGO_ALLOWED_HOSTS=localhost \
uv run python manage.py createsuperuser
```

Use the direct URL, not the `-pooler` URL, for `createsuperuser`, migrations, and
other one-off administrative commands.

Then open `https://<service>.onrender.com/admin/` and create:

- a fictional Church;
- separate fictional Admin, Pastor, Leader, and Member accounts as needed;
- ChurchMembership records with the intended roles.

Give each tester a separate temporary password through a private channel. Disable
the account after testing. There is no public registration flow yet.

## 4. Smoke test

After the deploy reports healthy:

1. Open `/api/health/` and confirm `{"status":"ok"}`.
2. Open `/` and sign in with a fictional test account.
3. Refresh a client route such as `/people` and confirm the SPA loads.
4. Open `/admin/` and confirm Admin CSS is present.
5. Confirm `/api/not-a-real-endpoint/` returns 404 rather than the React page.
6. Complete the fictional-data developer acceptance test.

Render Free spins down after about 15 minutes without inbound traffic. The first
request after sleep can take about one minute. Its filesystem is ephemeral;
Neon, not the container filesystem, stores the database.

## Deploys, rollback, and teardown

- Render deploys `codex/mvp-next` after linked GitHub checks pass.
- Review deploy logs after every change, especially migration output.
- Render Free can roll back to one of the two most recent deploys. A rollback
  changes application code only; it does not reverse database migrations or
  restore database data.
- For an application-only rollback, choose a previous successful deploy in
  Render. Use only backwards-compatible migrations in this demo branch.
- To stop testing without deleting data, suspend or delete the Render service.
- To destroy the demo completely, first delete the Render Blueprint/service,
  then delete the Neon project, and finally revoke all test credentials.
- Never delete Neon as a rollback mechanism unless all demo data may be lost.

## Cost guardrail

Keep exactly one Render Free web service and one Neon Free project. Do not add a
Render database, persistent disk, background worker, cron job, paid instance, or
paid Neon feature.

- Use a free Hobby workspace with no payment method. If the workspace already
  has a payment method, remove it before creating the demo.
- Check **Billing > Monthly Included Usage** regularly for free instance hours,
  outbound bandwidth, and build pipeline minutes.
- Without a payment method, Render suspends Free services after outbound
  bandwidth is exhausted and disables new builds after pipeline minutes are
  exhausted instead of charging for overage.
- Traffic from Render to the external Neon database uses the public internet and
  counts toward Render outbound bandwidth.
- Render's pipeline spend limit applies only to pipeline minutes. It does not cap
  outbound bandwidth charges, so it is not a substitute for removing the payment
  method.
