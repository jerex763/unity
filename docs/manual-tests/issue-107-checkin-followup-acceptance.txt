Unity #107 云端人工验收步骤
主题：首次到访 Follow-up 应在实际签到时创建，而不是在报名时创建

版本：2026-07-30
测试环境：https://unity-fictional-demo.onrender.com/

======================================================================
一、重要安全要求
======================================================================

1. 全程只使用虚构人物、虚构联系方式和虚构联系记录。
2. 不要输入真实姓名、真实电话、真实 Email、真实 WeChat ID、真实牧养资料。
3. 不要在真实教会或真实活动中执行本测试。
4. 所有测试人物姓名都使用本文给出的 “Issue107 Fictional ...” 前缀，方便最后清理。
5. 如果云端尚未部署包含 #107 的版本，请先停止测试；旧版本会在普通报名时错误创建 Follow-up。

======================================================================
二、通过规则摘要
======================================================================

必须同时满足以下规则才算通过：

1. 普通网上报名不会创建 Follow-up。
2. Visitor 第一次实际 Check in 后必须恰好有一条开放的 Follow-up。
   如果原来没有开放任务，创建 event_visit；如果已经有其他来源的开放任务，
   复用原任务，不覆盖 Source、负责人或 Interaction 历史。
3. Walk-in 会自动签到；没有开放任务时立即创建一条 event_visit Follow-up。
4. 签到前取消报名不会创建 Follow-up。
5. 重复签到、撤销后重新签到、参加后续活动，都不会创建重复 Follow-up。
6. 已经创建的 Follow-up 不会因取消报名、撤销签到或 Person 身份改变而被删除。
7. Newcomer、Regular、Member、Inactive 不会收到新人 event_visit Follow-up。
8. Pastor 能在 Follow-up queue 看到本教会所有已经产生的测试 Follow-up。
9. 其他教会的数据不可见；禁止访问应返回 404 或不显示数据。

五、场景 1：普通报名不创建 Follow-up
======================================================================

测试人物：Issue107 Fictional Advance Visitor
测试活动：Issue107 Fictional Check-in Event A

步骤：

1. 使用 Pastor 或 Leader 登录普通 Unity 页面。
2. 打开 Event A。
3. 在 Registration list 中选择 Issue107 Fictional Advance Visitor，创建普通报名。
4. 确认报名状态为 Registered，且操作按钮显示 Check in，而不是 Undo check-in。
5. 刷新页面。
6. 打开 Follow-up queue。
7. 搜索或检查 Issue107 Fictional Advance Visitor。
8. 再回到 Event A 的新增报名表单，重新选择同一个
   Issue107 Fictional Advance Visitor。
9. 在 Note 输入 “Fictional updated registration”，再次提交。
   这是用相同 Person 重新提交 upsert，不是寻找一个不存在的 Edit 按钮。
10. 确认仍是同一条报名，然后再次刷新 Follow-up queue。
11. 如需精确检查数据库字段，到 Django Admin → Events →
    Event registrations 打开该记录，确认 Checked in at 和 Checkin method 都为空。

预期：

- 普通报名创建成功。
- 用相同 Person 重提后更新同一条报名，没有创建第二条 Registration。
- 此人物没有出现在 Follow-up queue。
- Django Admin → Care → Follow ups 中也没有此人物的 Follow-up。

结果：Passed / Failed

九、场景 5：重复签到、撤销签到、重新签到和后续活动不重复创建
======================================================================

测试人物：Issue107 Fictional Checkin Visitor

A. 重复请求与撤销后重签

1. 在 Event A 中确认此人物的操作按钮是 Undo check-in。
2. 刷新 Event A，再次确认仍只有一条报名，按钮仍是 Undo check-in。
3. 执行一次 Undo check-in。
4. 确认操作按钮变回 Check in。
5. 刷新 Follow-up queue。
6. 确认原 Follow-up 仍存在，没有被删除。
7. 再次执行 Check in。
8. 确认操作按钮再次变为 Undo check-in。
9. 刷新 Follow-up queue。
10. 在 Django Admin → Care → Follow ups 中按 Person 搜索并计数。

预期：

- Undo check-in 不删除 Follow-up。
- 重新 Check in 不创建第二条 Follow-up。
- 此人物始终只有一条 event_visit Follow-up。

B. 后续活动

1. 为同一人物报名 Event B。
2. 报名后确认没有新增 Follow-up。
3. 在 Event B 对此人物执行 Check in。
4. 刷新 Follow-up queue。
5. 在 Django Admin 中再次按 Person 搜索并计数。

预期：

- Event B 的报名和签到都不创建第二条 first-visit Follow-up。
- 此人物仍只有一条 event_visit Follow-up。

   地址通常包含 `/admin/care/followup/<数字ID>/change/`。

C. 以当前教会 Pastor 验证列表隔离和精确 API 404

2. 使用 Fictional Test Church 的 Pastor 测试账号登录普通 Unity 页面。
3. 打开 Follow-up queue，确认搜索不到
   Issue107 Fictional Other Church Visitor。
4. 打开浏览器 Developer Tools → Console。
5. 把下面命令中的 OTHER_FOLLOW_UP_ID 替换为刚才记录的数字，然后执行：

   fetch('/api/follow-ups/OTHER_FOLLOW_UP_ID/', {
     credentials: 'same-origin'
   }).then(async response => {
     console.log('status=', response.status);
     console.log('body=', await response.text());

6. 查看 Console 输出的 status。

精确预期：

- `GET /api/follow-ups/<other-id>/` 返回 HTTP 404。
- Response body 不得显示其他教会 Person、Follow-up、负责人或 Interaction 内容。
- Follow-up queue 搜索不到其他教会人物。

- 在实际观察中写明无法执行的原因。
- 其余可执行项目继续测试，不要猜测 404 结果。

预期：

- Pastor 能看到本教会两条已经存在的测试 Follow-up。
- 是否属于 Pastor 自己的小组不影响 Pastor 的全教会可见性。
- 其他教会 Follow-up 不出现在列表中，精确 detail API 返回 404。

======================================================================
十三、失败判定
======================================================================

出现以下任一情况即为 Failed，并应截图及记录：

1. 普通报名后立即出现 Follow-up。
2. 签到前取消报名仍新建 Follow-up。
3. Visitor 第一次 Check in 后没有 Follow-up。
4. 一个人产生两条或以上开放 Follow-up，或后续活动重复创建 event_visit。
5. Walk-in 没有签到时间，或没有 Follow-up。
6. Undo check-in、取消报名或身份变化删除了已有 Follow-up/Interaction。
7. Newcomer、Regular、Member 或 Inactive 签到后产生新人 Follow-up。
8. Pastor 看不到本教会已经存在的 Follow-up。
9. 当前教会账号能看到其他教会的 Follow-up。
10. 页面看似隐藏，但直接访问 API 或对象 URL 仍泄露数据。
11. 已有开放 Follow-up 的 Source、负责人或 Interaction 历史被覆盖。

记录失败时请提供：

- 测试场景编号
- 账号角色
- Person 名称
- Event 名称
- 操作时间（Australia/Sydney）
- 实际结果
- 预期结果
- 截图
- 如可见，Registration ID 和 Follow-up ID

======================================================================
十四、测试后清理
======================================================================

只清理确认属于本次测试的虚构数据。

建议顺序：

1. Django Admin → Care → Interactions
   删除 Summary 含 “Fictional issue 107” 的测试 Interaction。

2. Django Admin → Care → Follow ups
   删除 Person 名称以 “Issue107 Fictional” 开头的测试 Follow-up。

3. Django Admin → Events → Event registrations
   删除 Event A 和 Event B 的所有 Issue107 测试 Registration。

4. Django Admin → Events → Events
   删除：
   - Issue107 Fictional Check-in Event A
   - Issue107 Fictional Check-in Event B

5. Django Admin → People → Persons
   删除名称以 “Issue107 Fictional” 开头、且确认没有非测试用途的 Person。

6. Django Admin → Tenancy → Churches
   删除 Issue107 Fictional Other Church。删除前确认其中只剩本次虚构测试数据。

7. 不要删除 Pastor、Leader 测试账号，除非这些账号本身也是本次临时创建且已确认无人使用。

8. 再次搜索 “Issue107 Fictional”，确认没有遗留测试记录。
